## 摘要
可见测试是LLM生成代码的常见门槛，但通过测试并不能证明规范正确性。我们研究一种类似部署的监控问题：在代码通过公共测试后，较弱的LLM验证器能否识别残留的隐藏错误？我们引入了代码监控红队测试，这是一种监控-红队测试协议，在固定公共检查信息边界的同时，改变生成器压力、验证器脚手架和弱到强能力。我们将其实例化为CodeMonitorBench，涵盖函数级、数据科学和工作流代码。在71,000个生成的候选项中，43,677个通过了公共测试，其中23,081个未通过隐藏测试。弱验证器通过脚手架和模型族有所改进，但在5%假阳性率下仍遗漏了大部分隐藏错误。作为鲁棒性压力测试，对抗性公共测试过拟合压力降低了验证器的AUROC，并在大多数单元格中提高了低FPR下的漏检率。GLM-5.1验证器在相同证据边界下恢复了一部分差距；可推断性审计显示，剩余的漏检混合了验证器失败和M1证据限制。

## Abstract
Visible tests are a common gate for LLM-generated code, but passing them does not certify specification correctness. We study a deployment-like monitoring problem: after code has passed public tests, can a weaker LLM verifier identify the residual hidden bugs? We introduce Code Monitor Red Teaming, a monitor-red-teaming protocol that fixes a public-check information boundary while varying generator pressure, verifier scaffolding, and weak-to-strong capability. We instantiate it as CodeMonitorBench, spanning function-level, data-science, and workflow code. Across 71,000 generated candidates, 43,677 pass public tests and 23,081 of those fail hidden tests. Weak verifiers improve with scaffolding and model family, but still miss most hidden bugs at 5% false-positive rate. As a robustness stress test, adversarial public-test-overfit pressure lowers verifier AUROC and raises low-FPR miss rates in most cells. A GLM-5.1 verifier recovers part of the gap under the same evidence boundary; an inferability audit shows that remaining misses mix verifier failures with M1 evidence limits.

## 2. 方法论：核心思想、关键技术细节

- **核心思想**：提出 **Code Monitor Red Teaming** 协议，将代码验证建模为“公开通过监控”。生成器可访问公开测试，代码先通过公开测试筛选，然后验证器（verifier）在固定信息边界（称为 **M1**）下对通过测试的代码进行评分，预测是否存在隐藏错误。隐藏测试仅用于事后标注，不参与验证器输入。
- **关键技术细节**：
    - **信息边界（M1）**：验证器仅接收：任务说明、接口、公开测试、候选代码、公开通过状态。不可见隐藏测试、隐藏执行结果、参考实现、聚合统计。
    - **生成器条件（Generator Pressure）**：5种压力条件：
        - G1：公开测试感知（基准）
        - G2：验证器感知（告知将受审查）
        - G3：方案感知（告知审查重点）
        - G4-natural：自然简化压力（不显式要求错误，但诱导过拟合）
        - G4-adv：对抗性压力（显式要求通过公开测试同时留下微妙隐藏错误，作为鲁棒性压力测试，非部署流行率估计）
    - **验证器脚手架**：两种审查方式：
        - Direct review：直接给出评分。
        - Hybrid review：先分解需求与边界案例，再进行反例导向审查后给出评分。两者使用相同M1证据。
    - **弱到强对比**：弱验证器（如Qwen-7B、Mistral-7B）与强验证器（GLM-5.1）在相同M1信息边界下比较。
- **公式/算法**（文字说明）：
    - 标注规则：每个候选代码经隐藏测试后标记为 HIDDEN-BUG（至少一个隐藏测试失败）或 CORRECT（全部通过）。
    - 验证器输出：数值怀疑分数 \( r(c) \in [0,1] \)，用于排序。
    - 指标：AUROC、AUPRC、固定FPR（如5%）下的TPR/FNR。NA行（超时、缺失、格式错误等）单独报告。

## 6. 主要结论与发现

1. **公开测试留下大量隐藏错误**：71,000候选中，43,677通过公开测试，其中23,081（52.8%）仍含隐藏错误。普通G1条件下隐藏错误率约43-47%，对抗性压力大幅提升。
2. **弱验证器在低FPR下漏检大部分隐藏错误**：在5%假阳性率下，Qwen-7B Hybrid漏检86.8%，Mistral-7B仍漏检80.0%。改进脚手架和模型族有所帮助，但不足以作为停止规则。
3. **对抗性压力降低监控分离度**：G4-adv使所有三个弱验证器的AUROC平均下降约0.07，FNR@5%FPR上升约0.07。这不是单纯增加错误数量，而是将错误推向验证器较难识别的区域。
4. **更强验证器仅部分恢复差距**：GLM-5.1在相同M1边界下，G1 FNR降至54.3%，G4-adv FNR仍为66.2%。这表明存在证据边界限制：部分隐藏错误难以从公开视图推断。
5. **可推断性审计**：92%的隐藏错误有规范依据，但仅33%可从公开视图构造性发现。强验证器捕获约40%，弱验证器仅20%。剩余漏检混合了能力失败和证据限制。

## 7. 优点

- **创新性**：将红队测试框架应用于代码监控，聚焦“公开通过后”这一高影响子集。
- **严谨的基准构建**：固定信息边界，分离构建效应与监控失败；提供三个代码领域，拓宽残差bug表面。
- **系统实验设计**：变化生成压力、脚手架、模型能力，全面揭示弱→强监控的局限性。
- **可推断性审计**：区分能力限制与证据限制，为未来改进提供方向（如改进验证器推理或增强公开证据）。
- **指标选择**：使用AUROC和固定FPR下的FNR，避免流行率敏感问题，适合监控场景（低误报预算）。

## 8. 不足与局限

- **隐藏标签局限**：依赖固定测试套件，不一定捕捉完整语义正确性；部分失败可能难以从公开视图推断。
- **基准覆盖有限**：仅涵盖函数级、数据科学和工作流；未覆盖所有编程场景（如仓库级、交互式开发、大型系统）。
- **对抗性压力非现实部署**：G4-adv是压力测试，不反映实际开发者错误频率。
- **未评估训练验证器**：未包括微调重排器等学习型验证器，也未评估生产级静态分析完整配置。

- **单次审查**：验证器仅单次推理，未应用多轮或投票策略（虽然脚手架变化属于推理结构变化）。

## 摘要
AI代理正迅速变得更为强大且广泛部署，有望带来显著的生产力提升并支持新型应用类别。然而，它们日益增长的自主性也引入了重大的隐私与安全风险。现有防御措施主要采用代理中心化方法，依赖代理自身来检测威胁并执行隐私与安全策略。这种方法存在根本性局限，因为它将策略执行委托给AI代理，而代理基于LLM的行为本质上具有不确定性，且容易受到提示注入等攻击手段的操纵。因此，当前防御措施无法可靠地防范隐私与安全威胁，凸显了亟需新解决方案来保障AI代理系统安全。网络社区长期以来面临类似挑战，并提供了富有洞察力的原则，我们可借鉴这些原则来设计更安全的AI代理系统。这些原则包括集中控制与分布式执行、基于能力访问以中介对敏感资源的请求，以及通过零信任执行实现最小权限。历史上，这些原则为网络系统提供了强有力的确定性保障。然而，仅凭这些原则不足以应对AI代理，因为代理行为的安全性与适当性往往取决于超出静态规则表达能力的语义上下文。基于这些原则，我们倡导一种系统性的AI代理安全方法，将提供强安全保证的确定性执行机制与支持细致决策的语义、上下文感知策略相结合。随后，我们提出一个参考架构，并识别关键研究问题与未来方向，以指导安全且保护隐私的AI代理系统的设计。

## Abstract
AI agents are rapidly becoming more capable and widely deployed, promising substantial gains in productivity and enabling new classes of applications. However, their growing autonomy also introduces significant privacy and security risks. Existing defenses are predominantly agent-centric, relying on the agent itself to detect threats and enforce privacy and security policies. This approach is fundamentally limited because it entrusts policy enforcement to AI agents whose LLM-driven behavior is inherently nondeterministic and vulnerable to manipulation through attacks such as prompt injection. As a result, current defenses cannot reliably prevent privacy and security threats, highlighting a critical need for a new solution to securing AI agent systems.   The networking community has long grappled with similar challenges and offers insightful principles we can borrow to design a more secure AI agent system. These include centralized control with distributed enforcement, capability-based access for mediating requests to sensitive resources, and least privilege through zero-trust enforcement. Historically, these principles have provided strong deterministic guarantees for networked systems. However, these principles alone are insufficient for AI agents because the safety and appropriateness of an agent's actions often depend on semantic context beyond the expressiveness of static rules.   Building on these principles, we advocate for a systematic approach to AI agent security that combines deterministic enforcement mechanisms, which provide strong security guarantees, with semantic, context-aware policies that enable nuanced decision-making. We then present a reference architecture and identify key research questions and future directions to guide the design of secure and privacy-preserving AI agent systems.

## 1. 论文的核心问题与整体含义（研究动机与背景）

- **问题定义**：AI 代理（基于 LLM 的智能体）正被大规模部署，可自主规划、推理并执行多步骤工作流（调用 API、操作工具、访问企业资源、与其他代理通信）。这种高度自主性带来了严重的隐私与安全风险，包括：敏感数据泄露、提示注入（prompt injection）、记忆投毒（memory poisoning）、目标劫持（goal hijacking）等。
- **现有防御的根本缺陷**：传统的安全架构依赖静态规则和预定义信任边界，无法适应代理行为的动态性、上下文相关性；而现有的 AI 代理防御（如提示级护栏、输出过滤器、模型微调、隐私感知提示）几乎全部是 **agent-centric（代理中心化）**——即把安全策略的解读和执行委托给代理本身。
- **核心矛盾**：代理的 LLM 行为本质上是**非确定性的**，且容易被对抗性输入绕过（如提示注入），因此**让代理自己保护自己**无法提供可靠的安全保证。作者指出：安全执行者和被约束方是同一个实体，这在逻辑上就是不可靠的。
- **论文主张**：应当将安全控制从代理内部**移到网络层面**——把网络视为天然的强制点（enforcement point），将多代理系统视为分布式通信系统，借鉴网络安全的成熟原理来保护它们。

## 2. 论文提出的方法论

### 核心思想：网络是天然的安全边界
- 网络安全社区面对的是“自治、多样、不可信的端点”之间的通信安全问题，几十年来积累了有效原则，可直接迁移到 AI 代理场景。

### 三大设计原则

1. **确定性强制 + 上下文感知语义控制（结合使用）**
   - 确定性强制：独立于代理模型权重、提示词或合作意愿，约束代理“能做什么”（调用哪些工具、访问哪些目标、数据流向哪里）。这是防火墙的代理执行图版本，而非基于 5-tuple。
   - 语义控制：采用 Nissenbaum 的**语境完整性（Contextual Integrity, CI）**理论，以 (发送者角色, 接收者角色, 主题, 信息类型, 传输原则) 形式定义信息流规范。将 CI 规范编译为可执行的检查函数，例如 `check_flow(sender, recipient, task, labels)`，在每跳上执行——本质上是信息流控制（IFC）+ CI 规范标签策略 + 网络作为参考监视器。
   - 关键论断：只靠确定性强制退化为粗糙的连通性控制（能阻止代理访问未批准端点，但不能阻止对已批准端点的过度分享）；只有语义而无确定性强制则退化为现有的可绕过护栏。

2. **集中控制（Centralized Control）**
   - 借鉴 SANE 和 Ethane（SDN 的基础）：由逻辑集中的控制服务器制定声明式高層策略，网络设备只负责执行下发的规则。
   - 对 AI 代理：控制平面放在代理无法触及的受信任边界内，防止代理绕过或篡改策略。
   - 作者引用端到端论证（Saltzer et al.）：当端点无法完整可靠地实现某功能时，应将该功能放入网络。代理自身不可信，因此安全功能必须放在代理之外的网络中。

3. **基于能力的最小权限访问（Capability-based Access / Off-by-Default）**
   - 借鉴 SIFF、TVA、Off-by-Default 的能力交换思想。
   - 代理默认不可访问任何外部目标；每个任务只授予一个**窄范围、可撤销的能力**，明确指定：允许的目的地、可共享的数据类型、传输目的。
   - 能力必须**防伪造、可验证**，由受信策略权威颁发，而非代理自己声明。

### 参考架构（核心贡献）

- **控制平面（Control Plane）**：位于企业信任边界内，与代理隔离。负责定义和分发策略（确定性 ACL/RBAC、语义策略如“客户 PII 如何使用”、请求路由策略、数据敏感度标签、风险阈值、用于语义评估的已批准模型）。
- **Sidecar（伴生代理）**：部署在代理旁边，位于代理与外部资源的中间，是唯一的运行时强制点。由四个组件构成：
  - **Agent Policy Gateway**：拦截代理的所有外部操作（工具调用、内存操作、API 请求、网络通信、文件访问、数据共享），执行最终决策。
  - **Request Classifier / Policy Router**：根据政策定义的标准（动作类型、资源敏感性、风险级别）将请求路由到确定性引擎或语义引擎（风险自适应路由）。
  - **Deterministic Enforcement Engine**：对 ACL、RBAC、工具权限、网络策略、速率限制等无歧义规则做快速确定性的放行/拒绝（可直接在数据平面实现，作者对比了P4和eBPF两种路径）。
  - **Context-Aware Semantic Engine**：收集执行上下文（数据敏感性、动作风险、代理角色、用户意图、任务状态、近期交互历史），评估语义策略，输出 allow / deny / modify / redact / escalate for human approval。
- **执行流**：控制平面 → 下发策略到 sidecar → 代理发起外部动作 → Gateway 拦截 → Classifier 路由 → 确定性引擎评估（无需语义场景）或语义引擎评估 → 决策返回 Gateway 执行。当前实现流程中，语义引擎使用被评估的数据、动作风险、权限、意图、任务状态和最近交互构建结构化上下文，但它接收的 token 流并非所有都是相关/可信的，因此需要将可验证的执行历史作为输入。所有决策记录在案，用于审计和策略改进。

## 6. 论文的主要结论与发现

- **现有防御根因不可靠**：将安全委托给行为不可预测、可被操纵的 LLM 代理，注定无法提供强安全保证。
- **网络是正确的位置**：多代理系统本质上是分布式通信系统，网络边界正是实施安全控制（数据最小化和出口控制）的天然位置。
- **两种抽象必须结合**：确定性强制提供强安全保证；上下文感知策略（CI 理论）提供语义判断的细致度。单独使用任何一种都不够。
- **参考架构可行**：通过“集中控制平面 + 代理旁路 sidecar”的架构，可以在不修改代理实现、不依赖代理合作的前提下，拦截和执行安全策略。
- **关键开放问题**：动态代理的运行时代码更新需要将规则表达从静态 ACL 扩展为某种动态可更新结构；当受保护资源是上下文隐私信息而非网络带宽时，能力机制的正确粒度与语义不明；Ingress 比 egress 更难，因为依赖恶意发送者的合作不可行。

## 7. 优点

- **跨领域视角新颖**：将网络安全数十年的成熟原理（SDN 集中控制、能力访问、Off-by-Default、零信任、信息流控制）系统性地迁移到 AI 代理安全，角度独特且论证扎实。
- **直击要害的问题诊断**：准确识别了 agent-centric 防御的逻辑死穴——被保护者即执行者。引用的端到端论证非常贴切。
- **概念上的深度拓展**：将 CI 理论从“评估工具”（此前多数工作只用来测泄漏率）转化为可执行的强制语义，并明确提供了形式化接口（check_flow 函数），这是一步理论创新。
- **设计原则清晰、可操作**：提出的三大原则（确定性+语义结合、集中控制、能力访问）有文献支撑（SANE/Ethane/SIFF/TVA），每一步都有对应的网络先驱类比。
- **架构具备部署可行性**：Sidecar 安全层独立于具体代理框架，可与 API 网关、服务网格、企业身份管理系统集成，且不要求修改代理本身。

## 8. 不足与局限

- **缺乏实验验证**：架构未实现原型、未做端到端评估，无法验证性能开销（语义引擎的延迟、吞吐影响）、安全有效性（能否抵抗各类攻击）等关键指标。
- **攻击面未完全消除**：语义引擎依赖代理提供的上下文信息；攻击者仍可能通过操纵上下文来欺骗语义引擎——作者承认这一点，但未提供充分的缓解机制。
- **仅解决出口（egress）**：架构只管代理发出的数据，对入站（ingress）流量无控制能力；而且作者承认“若发送者合作则无法检查入站流量”这一固有限制。要解决需要新策略，例如依赖于预先商定的 sender-attached 可验证标签。
- **泛化性不足**：静态规则难以为运行时动态创建的子代理（sub-agents）、新工具、未见交互做策略支持；动态角色/信任等级的持续再评估成本高。
- **策略循环的智能问题未完全解决**：风险感知策略路由器本身如何设计、语义引擎的智能边界（什么内容属于它的“政策词汇”而超出语音识别管道的能力）等关键问题仍开放。
- **部署壁垒未讨论**：实际部署需要与既有基础设施协调、策略迁移成本等现实问题，论文着墨不多。

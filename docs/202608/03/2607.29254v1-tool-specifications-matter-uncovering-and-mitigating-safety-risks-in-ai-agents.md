## 摘要
AI代理通过外部工具扩展大语言模型（LLM），使其能够执行复杂任务并将模型输出转化为实际世界中的重大行动。然而，LLM在作为代理部署时往往会变得明显不安全，而这种退化的根源仍知之甚少。在本文中，我们识别出模式化格式的工具规格是代理安全性退化的主要原因，并通过白盒表示分析表明，它们削弱了模型内部的拒绝信号，并导致不安全的工具执行。基于这一发现，我们提出了SafeKeep，一种推理时的安全防护措施，它将安全判断与工具执行解耦：它在使用扁平化文本工具规格评估请求的同时，保留原始模式化格式的规格用于执行。在两个代表性基准和四个LLM（包括白盒和黑盒模型）上，SafeKeep将有害请求的平均拒绝率从23.8%提高到70.6%，并将观察级提示注入下的平均攻击成功率从25.6%降低到2.5%。它还优于现有的安全防护措施，并保持了任务处理能力。我们在https://github.com/snowcatsmoking/SafeKeep 发布了代码和数据。

## Abstract
AI agents extend large language models (LLMs) with external tools, enabling them to perform complex tasks and translate model outputs into consequential real-world actions. Yet LLMs often become substantially less safe when deployed as agents, and the source of this degradation remains poorly understood. In this paper, we identify schema-formatted tool specifications as a primary source of agent safety degradation and show, through white-box representation analysis, that they weaken the model's internal refusal signals and contribute to unsafe tool execution. Building on this finding, we propose SafeKeep, an inference-time safeguard that decouples safety judgment from tool execution: it assesses requests using flattened textual tool specifications while retaining the original schema-formatted specifications for execution. Across two representative benchmarks and four LLMs, including both white-box and black-box models, SafeKeep increases the average refusal rate for harmful requests from 23.8% to 70.6% and reduces the average attack success rate under observation-level prompt injection from 25.6% to 2.5%. It also outperforms existing safeguards and preserves task-handling capability. We release the code and data at https://github.com/snowcatsmoking/SafeKeep .

## 1. 核心问题与整体含义（研究动机和背景）

- **研究背景**：AI代理（AI agents）通过外部工具扩展LLM的能力，使其能够执行信息检索、API调用、代码执行等复杂任务，将模型输出转化为真实世界行动。然而，多个近年研究发现，同一个LLM在聊天场景下能拒绝有害请求，一旦部署为代理后却可能服从这些请求，出现明显的安全性退化。
- **核心研究问题**：为什么一个在聊天场景下会拒绝有害请求的LLM，在部署为代理后变得不再可靠？这种安全退化的根本原因是什么？
- **研究意义**：AI代理的安全失败比聊天机器人的安全失败更严重——不安全的聊天回复还只是文本，而不安全的代理回复可能导致隐私泄露、操纵外部服务、触发真实世界行动等实际危害。因此，了解并缓解代理安全退化是安全部署AI代理的前提条件。
- **核心发现**：论文通过白盒表示分析，识别出**schema格式化的工具规格（schema-formatted tool specifications）** 是代理安全退化的主要来源，并揭示了其背后的机制：schema格式化引入了一个与拒绝方向相对立的隐藏状态方向，削弱了模型内部的拒绝信号，从而促进不安全的工具执行。

## 2. 论文提出的方法论

### 2.1 核心思想
论文的核心思想分为两个层面：
1. **诊断层面**：通过白盒表示分析定位安全退化的来源，即schema格式化的工具规格，并揭示其作用机制。
2. **缓解层面**：基于上述机制提出SafeKeep，一个推理时安全防护框架，将安全判断与工具执行解耦，用扁平化文本工具规格进行安全评估，保留原始schema格式工具规格用于执行。

### 2.2 关键分析技术

**（1）拒绝方向（Refusal Direction）提取与AUROC评估**

论文遵循Arditi等人（2024）的拒绝方向提取方法，定义为有害请求和良性请求的最终token隐藏状态均值之差：

$$\hat{r}_f = \frac{r_f}{\|r_f\|}$$

对于未见输入，通过计算其最终token隐藏状态在拒绝方向上的投影作为拒绝分数，并利用AUROC衡量有害与良性请求的可分离性。

**（2）组件级消融分析**

将代理上下文分解为三个组件——代理角色描述（role description）、工具使用指令（tool-use instructions）、工具规格（tool specifications），增量添加到聊天基线中，使用固定的聊天场景下提取的拒绝方向作为共享探针，评估每个组件对安全表示质量的影响。

**（3）表示与语义的解耦分析**

- **表示转换（representation conversion）**：将schema格式的工具规格转为扁平化文本表示，去除JSON语法、保留字段、嵌套、类型声明和必填标记，同时保留工具名称、功能描述和参数含义。
- **语义随机化（semantic randomization）**：用长度相近的可发音伪词替换工具名称、描述、参数名和参数描述，保留结构组织但去除语义信息。

**（4）Schema方向的识别与验证**

定义Schema方向为同一工具规格以schema格式与扁平文本格式呈现时模型最终prefill token隐藏状态的平均差异：

$$R_c^{(\ell)} = \mathbb{E}_{x \in D_c}\left[h_{\text{schema}}^{(\ell)}(x) - h_{\text{text}}^{(\ell)}(x)\right], \quad c \in \{\text{harmful}, \text{benign}\}$$

对有害和良性请求分别估计方向，然后计算该方向与拒绝方向的余弦相似度随层的变化。

**（5）因果验证（激活引导）**

在拒绝AUROC最高的层，通过减去归一化的有害请求Schema方向来干预模型激活：

$$\tilde{h}^{(\ell^*)} = h^{(\ell^*)} - \alpha \hat{R}_{\text{harmful}}^{(\ell^*)}$$

以此验证Schema方向对不安全行为的因果贡献。

### 2.3 SafeKeep 方法框架

SafeKeep包含两个阶段：

**第一阶段：安全判断（Safety Judgment）**
- 构建安全评估上下文，包含安全评估者角色、原始代理角色和指令、**扁平化文本工具规格**（而非schema格式）、以及待评估的用户请求。
- 模型输出YES表示执行该请求不安全，NO表示安全。
- 此阶段使用与原始代理相同的LLM，无需微调或访问内部激活。

**第二阶段：执行控制（Execution Control）**
- 若判定为NO（安全），将请求转发至未修改的原始代理pipeline，schema格式工具规格保持不变以支持工具选择与执行。
- 若判定为YES（不安全），阻止工具使用，预填一个简短的拒绝前缀（如"I'm sorry, but I can't help with that."），让模型自回归生成更自然的、请求特定的拒绝回复。

**关键设计**：解耦安全判断与工具执行，避免schema格式工具规格对安全判断的干扰，同时保留原始工具接口用于执行。

## 3. 实验设计

### 3.1 数据集与基准（Benchmark）

- **ToolSafety**：用于构建配对数据集，包含400个有害请求，使用Claude Sonnet 4.6将每个请求最小改写为对应的良性请求，形成400个有害-良性配对（7:3划分用于方向提取和评估）。用于源码定位和机制分析。
- **AgentHarm**：包含11个危害类别的多样化代理任务，使用其评估集（176个有害请求+176个匹配良性请求）。报告指标：准确率（Acc）和拒绝率（Refusal）。
- **InjecAgent**：间接、观察级提示注入基准，1054个攻击案例。报告指标：基础设置的有效率（Valid-B）/攻击成功率（ASR-B），增强设置的有效率（Valid-E）/攻击成功率（ASR-E）。

### 3.2 评估的LLM后端

四个代表性LLM，涵盖开源白盒和专有黑盒模型：
- Llama3.1-8B-Instruct（开源白盒）
- Qwen3-8B（开源白盒）
- Gemini3.1-Flash（专有黑盒）
- GPT5.4-mini（专有黑盒）

### 3.3 对比方法（Baselines）

- **Base**：无任何额外防护的原始代理。
- **SafeJudge**：使用SafeKeep的两阶段pipeline但保留schema格式工具规格进行安全判断，用于隔离扁平化表示的作用。
- **SafePrompt**：在输入中附加AgentHarm安全提示，描述常见有害请求类别并指示代理拒绝它们。
- **SafeHarbor**：近期提出的代理特定安全防护，对抗性生成上下文相关安全规则，存储在层次记忆中，推理时检索相关规则。

### 3.4 分析实验设置

- 机制分析使用Llama3.1-8B-Instruct，在配对数据集上评估不同输入配置下的AUROC。
- 组件级消融在Llama3.1-8B-Instruct、Qwen3-8B、Mistral-7B-Instruct-v0.3三个开源模型上进行。
- 增加了长度匹配的聊天控制（Chatbot-Long）以排除上下文长度的影响。

## 6. 主要结论与发现

### 6.1 源码定位
- **工具规格是安全退化的主导来源**：添加工具规格造成的AUROC平均下降0.136，远大于其他组件。增加上下文长度（Chatbot-Long）不足以解释退化，说明是工具规格的内容而非长度导致问题。

### 6.2 机制层面
- **表示形式而非语义内容起作用**：将schema格式转换为扁平文本（保留语义）显著改善AUROC（如Llama上0.740→0.885），而语义随机化（保留schema格式）几乎没有改善（0.776），表明安全退化由表示形式驱动。
- **Schema方向与拒绝方向对立**：有害请求的Schema方向在每一层都与聊天场景的拒绝方向呈负余弦相似度，说明schema格式将有害请求的内部表示推向与拒绝相反的方向。
- **解码后效应持续**：在首个生成token处，schema格式显著降低有害与良性请求在拒绝方向上的分离度。
- **因果验证**：在峰值拒绝层减去harmful Schema方向，将拒绝率从5.0%提升至47.5%（α=4），同时有害执行从95.0%降至45.0%；但过度干预（α=12）导致全部输出无效，说明该方向的因果贡献。

### 6.3 SafeKeep有效性
- **安全性能大幅提升**：四个LLM上，AgentHarm拒绝率均值从23.8%提升至70.6%；InjecAgent总体攻击成功率从25.6%降至2.5%（ASR-B从26.5%降至2.3%，ASR-E从24.7%降至2.7%）。
- **任务处理能力保持乃至提升**：AgentHarm准确率从60.9%提升至79.6%；InjecAgent的Valid-B/Valid-E均值从78.7%/78.8%提升至93.0%/94.8%。
- **扁平化表示至关重要**：相比使用schema格式做安全判断的SafeJudge，SafeKeep的拒绝率从45.0%提升至70.6%，证明扁平化文本表示对可靠安全评估的关键作用。
- **优于现有防护**：在12个LLM-安全指标组合中，SafeKeep在11个中取得最佳或并列最佳结果。

## 7. 优点

1. **问题定位精准且有深度**：首次将代理安全退化归因于工具规格的表示形式（而非语义内容），从表象问题深入到内部表示机制，诊断链条完整。
2. **多层级证据链完整**：从行为现象（拒绝率下降）→表示分析（AUROC下降）→机制解释（Schema方向对立）→因果验证（激活引导）形成完整的证据链条，论证扎实。
3. **有效的受控实验设计**：
   - 使用配对数据集（有害-良性改写），控制除安全标签外的变量；
   - 长度匹配控制（Chatbot-Long）排除上下文长度混淆；
   - SafeJudge基准隔离扁平化表示的作用；
   - 语义随机化与表示转换的双向解耦实验设计巧妙。
4. **方法轻量且通用**：SafeKeep无需参数更新、无需访问模型内部激活，可同时应用于开源和闭源模型，不改变底层代理及其工具接口，实际部署门槛低。
5. **强调任务能力保持**：不仅报告安全指标，还报告有效率和准确率，避免了“一刀切拒绝”的简单策略，确保安全提升不损害正常功能。
6. **代码数据开放**：公开代码和数据，利于后续研究复现和扩展。

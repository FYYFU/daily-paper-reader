## 摘要
编码代理越来越多地在组织内部运行，其安全控制（如作用域凭据、受限出口、只读文件系统、非根执行）像约束任何其他软件一样约束着它们。然而，现有基准几乎完全在宽松的沙箱中评估代理，因此当执行策略时性能如何变化尚属未知。在本工作中，我们基于常见的真实世界企业限制，在Terminal-Bench 2.1上评估了12个编码代理，跨越嵌套的安全策略级别。硬化从来不是免费的，但远非均匀：在最严格的策略下，成功率损失高达18.3个百分点，成本膨胀达167.3%，且这两个指标并不一致；最能保持成功率的模型同时也是效率损失最大的模型，因此模型选择取决于策略。除总体得分外，我们还刻画了当策略阻止代理行动时代理的行为，并分解了硬化引发的失败：运行陷入超时或错误解决方案，而非提前停止，且不同模型的失败模式组合不同。为了给比较提供依据，我们验证了最严格策略下任务的可解性，将模型失败与策略排除的任务区分开来。我们发布了Boundary-Bench，一个开源硬化插件，可在Terminal-Bench及兼容基准上对编码代理进行策略约束评估。

## Abstract
Coding agents increasingly run inside organizations whose security controls (scoped credentials, restricted egress, read-only filesystems, non-root execution) constrain them like any other software. Existing benchmarks, however, evaluate agents almost exclusively in permissive sandboxes, so it is unknown how performance changes when policy is enforced. In this work, we evaluate 12 coding agents on Terminal-Bench 2.1 across nested security policy levels derived from common real-world enterprise restrictions. Hardening is never free but far from uniform: under the strictest policy, success losses reach 18.3 points and cost inflation 167.3\%, and the two axes disagree; the model that best preserves success is also the one that loses the most efficiency, so model choice is policy-dependent. Beyond aggregate scores, we characterize how agents behave when policy blocks their actions and decompose the failures hardening induces: runs grind into timeouts or wrong solutions rather than stopping early, in a mix that differs by model. To ground comparisons, we verify task solvability under the strictest policy, separating model failures from tasks the policy forecloses. We release Boundary-Bench, an open-source hardening plugin enabling policy-constrained evaluation of coding agents on Terminal-Bench and compatible benchmarks.

## 论文总结：权限拒绝——硬化环境中编码代理的政策分级评估

### 1. 核心问题与整体含义

- **研究背景**：编码智能体（Coding Agents）正越来越多地在企业内部运行，不可避免地受到企业现有安全策略的约束。这些控制机制包括作用域凭据（scoped credentials）、受控网络出口（restricted egress）、只读文件系统（read-only filesystems）和非根执行（non-root execution）等，其约束对象是环境中运行的任何软件，而非针对智能体本身。
- **现实脱节**：现有主流编码智能体基准（如 Terminal-Bench、SWE-bench 等）几乎全部在宽松沙箱中评估，让智能体以 root 权限自由操作容器，这与真实企业部署环境存在系统性差异。因此，**当前排行榜很可能无法反映智能体在受控环境中的真实性能表现**。
- **核心研究问题**：当安全策略被强制执行时，编码智能体的任务成功率和运行成本会发生怎样的变化？这种影响在不同模型之间是均匀的还是具有显著异质性？其背后的行为机制是什么？
- **整体含义**：本文的研究结论表明，安全硬化（hardening）不是"免费的"，但也远非均匀——不同模型以不同"货币"（成功率下降或成本膨胀）为代价，模型选择的优劣排序会随策略等级的改变而改变，因此**模型选择必须在目标部署策略下进行才有意义**。

### 2. 方法论

#### 核心思想：将安全策略作为自变量，而非固定配置

- **Boundary-Bench 框架**：一个开源硬化插件，在现有编码智能体基准（Terminal-Bench 2.1）之上叠加可配置的操作系统级策略，系统性地测量智能体性能随策略收紧的变化。
- **三个策略等级**（从松到严递进）：
  - **Control（开放基线）**：root 权限、无限制网络出口、可写文件系统。
  - **Non-root（非根）**：仅删除 root 权限，网络与文件系统保持开放，用于隔离非根执行的单独影响。
  - **NIST-derived high（严格级）**：三个维度同时锁定——网络出口白名单（205 个域名）、只读文件系统（工作区外全只读）、完全权限封锁（无特权提升通路）。
- **三个硬化轴及其 NIST 映射**：
  - **网络（Network）**：所有出口流量强制经过不能重配置的代理，默认拒绝白名单之外的域名。映射到 SC-7 边界保护控制族。
  - **文件系统（Filesystem）**：操作系统目录挂载只读，仅工作区与临时路径可写。映射到 AC-3、AC-4、SC-39 等访问和信息流控制。
  - **权限（Privilege）**：以专用非特权用户运行，无 sudo 条目、root 密码锁定、no_new_privs 设置、能力集清空。映射到 AC-6 最小权限族。
- **强制方式**：所有限制均由原生 Linux 内核机制（代理、bind-mount、setpriv/nftables）在环境中编译强制，而非向智能体请求；智能体只会遇到普通系统错误（HTTP 403、EROFS、EPERM）。所有子进程继承限制，无法通过启动子进程规避。
- **预检探针（Pre-flight probes）**：每次运行前验证每条限制是否生效，并测试绕过尝试（嵌套 shell、裸 IP 出口等），失败即关闭（fail closed）。

#### 基准审计流程

- **可解性验证（Solvability witness）**：在最严格策略下重放官方参考解，若失败则自行编写符合策略的参考解；两者都不行则判定为"被设计阻塞"（blocked by design）。
- **验证器修复（Verifier repair）**：对 5 个因验证器过度指定（over-specification）而拒绝合法解的任务，以"仅加性放宽"原则修复断言，统一应用于所有策略等级。
- **失败分类**：将失败运行按其结束位置相对时间预算分类为超时（timeout）、提前停止（early stop）和错误解（wrong solution）。

#### 鲁棒性度量公式

- 成功率变化（绝对百分点）：ΔSRm(ℓ) = SRm(ℓ) − SRm(control)
- 成本变化（相对百分比，按基线自身成本归一化）：ΔCm(ℓ) = 100 × [Cm(ℓ) − Cm(control)] / Cm(control)

该归一化方式使得绝对值相差数个数量级的模型之间的成本膨胀可比。

### 3. 实验设计

- **基准**：Terminal-Bench 2.1 全部 89 个任务。
- **测试对象**：12 个模型-框架捆绑（frozen model-harness bundle）：
  - OpenAI 系列（GPT-5.6 Sol / Terra / Luna）→ Codex CLI；
  - Anthropic 系列（Claude Sonnet 5 / Opus 4.8 / Fable 5 / Opus 5）→ Claude Code；
  - xAI（Grok 4.5）→ Grok Build；
  - 开源权重系列（Kimi K3、GLM-5.2、Qwen3.7 Max、MiniMax M3）→ Terminus-2。
- **三种策略条件**：Control、Non-root、NIST-derived high。
- **主要实验**：每个 bundle-task-policy 单元恰好 3 次有效试验，总计 9,612 次主要运行。
- **深度采样实验**：选择 2 个任务（compile-compcert 成功率基本保持；caffe-cifar-10 成功率骤降），用 GPT-5.6 Luna–Codex 在控制与硬化条件下各跑 100 次，分析成本分布机制。
- **模型-框架消融实验**：将 GPT-5.6 Luna（低成本端）与 Grok 4.5（高成本端）交叉配对 Codex 与 Grok Build，共 2×2 组合，测试效果归因于模型还是框架。
- **对比基线**：与 CaMeL、Progent、Verifier Tax 等单点硬化评估方法对比，本文是首个将策略严重度作为独立变量的基准研究。

### 5. 实验数量与充分性

- **主实验矩阵**：12 模型 × 89 任务 × 3 策略 × 3 次重复 = 9,612 次运行，覆盖完整任务集，规模可观。
- **深度采样**：2 任务额外 400 次运行（每任务每条件 100 次），用于机制归因。
- **消融实验**：2×2 模型-框架交叉 × 3 策略 × 89 任务 × 3 次 = 3,204 次运行。
- **任务诊断**：逐一审计全部 89 个任务的可解性，修复 5 个验证器，撰写 32 个策略合规参考解。
- **充分性评价**：
  - **优点**：任务覆盖完整（89 个全任务而非子集）；多策略分级设计可描绘 Pareto 前沿移动；深度采样与消融实验增强了机制层面的说服力；验证器审计和可解性区分避免了将策略导致的不可解误归因于模型。
  - **不足**：每单元仅 3 次重复，点估计无置信区间，论文也明确提醒"小差异不应过读"；仅覆盖单一基准（Terminal-Bench）；深度采样只在 2 个任务上进行，外推性有限；模型间存在框架差异（各用自家 harness），效果无法纯归因于模型权重。

### 6. 主要结论与发现

- **硬化非均匀地使所有模型劣化**：在最严格策略下，所有 12 个 bundle 的成功率下降且成本上升，但幅度差异显著：成功率损失最高达 18.3 个百分点（Claude Sonnet 5），成本膨胀最高达 167.3%（Grok 4.5）。
- **权衡普遍存在，但货币不同**：Grok 4.5 牺牲成功率最少（−7.1pp）但成本膨胀最高；GPT-5.6 Luna 成本膨胀最小（+16.0%）但成功率损失几乎最大（−18.0pp）；两个指标并不一致，不存在两个维度同时最优的模型。
- **Pareto 前沿随策略下移右移**：模型排序在硬化下重新洗牌，最优模型选择依赖具体策略等级。
- **失败模式是"磨死"而非"放弃"**：增加失败主要为超时（12.0%→16.4%）和错误解（12.8%→15.5%），提前停止几乎不变（2.4%→2.7%）；硬化下通过运行平均多 13% 时间、14% 工具调用、26% token。
- **成本膨胀高度集中在策略影响任务**：参考解不兼容的 32 个任务上成本为基线的 2.59 倍，参考解兼容的 50 个任务几乎不变（1.14 倍）；83.5% 的额外失败集中在受影响子集。
- **成本压力不随成功与否转移**：深度采样中成功保持与骤降的任务成本中位数均涨约 3 倍，且失败运行的成本与通过运行相近——策略性失败消耗完整膨胀预算。机制归因显示 97% 的额外成本来自绕行路径构建。
- **任务可解性区分了模型失败与策略排除**：82/89 任务在最严格策略下有可解性证据（50 个官方参考解直接通过，32 个为自撰合规解）；7 个任务被设计阻塞，其中 1 个（count-dataset-tokens）发现了验证器仅检查答案字符串的基准完整性缺陷。
- **阻塞动作暴露集中且可预测**：egress 拒绝占阻塞量 90.5%，且以高持久性为特征（平均每试验 10.5 次）；阻塞在任务间极度集中（5 个任务承担约一半量）；阻塞暴露度从不受影响子集（14.4% 试验）到受影响（51.6%）到被阻塞任务（67.8%）单调上升。

### 7. 优点与亮点

- **首次将策略严重度作为自变量**：此前研究（CaMeL、Progent 等）均在单个固定配置下评估，本文的三级嵌套阶梯设计能揭示前沿移动方向和权衡结构。
- **真实操作系统级强制**：限制由原生内核机制（代理、bind-mount、setpriv）实施，非提示词请求，智能体只能以原生错误形式感知，生态效度高；且子进程继承限制，不可规避。
- **严谨的任务可解性审计**：区分"模型失败"与"策略使任务不可解"，避免将环境责任错误归因于模型；撰写 32 个策略合规参考解体现了较高的工程投入。
- **验证器修复遵循保守原则**：仅加性放宽过度指定的断言，保留所有实质性检查，且统一应用于所有策略等级，不偏袒任何条件。
- **失败归类的正交设计**：以运行结束位置（相对预算）分类，而非主观判断，结果揭示"磨死而非放弃"的清晰模式。
- **成本归因提供可操作预测**：参考解兼容性在运行任何智能体之前即可计算，可预测策略在何处会"花钱"和"降分"，具有实际部署指导价值。
- **开源发布**：Boundary-Bench 代码、全部原始数据、验证器 diff 与实验溯源均发布，便于复现与扩展。

### 8. 不足与局限

- **单一基准限制**：所有证据来自 Terminal-Bench 及其 89 个任务；扩展到其他基准需要重复完整的可解性审计、参考解撰写与推理开销。结论仅在此基准上成立。
- **每单元 3 次重复的置信度限制**：主要实验以 3 次有效试验为单元，无置信区间，Pareto/排序判定为描述性而非统计性；深度采样仅覆盖 2 个任务。
- **效果归因停留在 bundle 层**：模型与其框架捆绑评价，无法将观察到的差异归因于模型权重或 harness 单独；模型-框架消融只覆盖 Pareto 前沿的两个成本极端。
- **安全分类器的干扰**：OpenAI 与 Anthropic 服务层

- **安全分类器的干扰（续）**：OpenAI 与 Anthropic 的服务层自带安全分类器，可能拦截或改写输出，这引入了与操作系统级策略无关的额外变量。硬化环境中模型更多次地探测边界，可能更频繁触发服务层审查，从而混淆"策略导致的失败"与"分类器导致的失败"。论文未单独报告或控制这一干扰，因此部分模型的成本膨胀可能包含安全服务的贡献。

- **网络白名单的单一快照性**：NIST-derived high 采用的 205 个域名白名单是作者从企业文档中归纳出的一个快照，不代表所有企业策略。不同企业白名单的宽窄与构成会显著影响阻塞分布，因此文中的"受影响任务子集"清单具有特定性，不能直接迁移到其他策略配置。

- **成本度量维度单一**：成本以美元为唯一聚合货币，未系统报告 token 消耗、墙钟时间、工具调用数之间的相对贡献变化。虽然文中给出平均 13% 时间、14% 工具调用、26% token 的增量，但未按模型分解这些子项如何汇入美元成本，实践者难以据此预估自身计费模式下的成本。

- **策略轴不连续**：三级策略（开放、非根、严格）在三个轴上同时变动，从 Non-root 到 NIST-derived high 的跳跃包含网络、文件系统、权限三个维度的同时叠加，无法区分各轴单独的边际贡献。论文未做单轴消融（如仅只读文件系统、仅网络白名单），因此"哪条策略最昂贵"这一问题尚无答案。

- **安全收益未被量化**：论文系统测量了安全策略的性能代价，但未对策略的安全收益（如攻击面缩减、凭据泄露概率下降）做任何量化。这使得"代价-收益"的完整图景缺失，实践者无法判断某一策略等级下的成本膨胀是否"值得"。

- **端点时序与路由不确定性**：所有模型推理经 OpenRouter 路由至厂商端点，路由策略、端点负载、模型版本漂移可能在实验期间引入额外方差。论文未报告每次运行的时间戳分布或端点信息，复现时无法完全对齐服务端条件。

### 9. 总体评价与启示

- **对模型选择实践的直接影响**：本文最重要的实践含义是——**排行榜必须在目标部署策略下重跑才有决策价值**。在 Control 下排名靠前的模型（如 Grok 4.5 的成本效率优势）在严格策略下可能被成本膨胀抵消；反之，某些在控制条件下表现中庸的模型可能在硬化环境中展现更好的鲁棒性。企业在选型时应将候选模型置于自身安全策略等级下做小样本评测，而非直接采信开放沙箱的基准分数。

- **对成本预算规划的影响**：83.5% 的额外失败集中在策略受影响子集的发现，意味着企业可以在部署前通过"参考解兼容性检查"这一廉价静态分析，识别出哪些任务/工作负载将在硬化环境中产生不成比例的成本与失败风险，从而提前调整预算或修改任务分解方式。

- **对基准社区的呼吁**：本文隐含地批评了现有编码智能体基准的生态效度。若未来基准默认至少包含一个硬化策略条件，并强制披露每次运行的具体策略配置，则整个领域的性能比较将更具现实可迁移性。Boundary-Bench 作为一个开源插件，为既有基准附加策略维度提供了低成本路径。

- **对智能体行为研究的贡献**："磨死而非放弃"的失败模式刻画和"绕行路径构建占额外成本 97%"的机制归因，为理解智能体在受限环境中的行为策略提供了定量证据：智能体倾向于坚持尝试合规路径而非提前放弃，这一性格需要在未来的对齐与效率设计中予以重视。

- **总体判断**：本文是首个将安全策略严重度作为自变量系统评估编码智能体的研究，方法论上具有开创性，工程实现严谨（内核级强制、可解性审计、验证器保守修复），结论在 Terminal-Bench 范围内具有较高可信度。其局限（单基准、少重复、bundle 级归因）决定了结论应被视为方向性证据而非最终定论，尤其不应外推至所有编码场景。

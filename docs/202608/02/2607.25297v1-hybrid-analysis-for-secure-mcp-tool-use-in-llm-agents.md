## 摘要
大语言模型（LLM）代理的快速发展使其能够广泛应用于各种真实世界任务。为标准化LLM代理与外部环境之间的交互，模型上下文协议（MCP）工具已成为事实上的标准，并被广泛集成到这些系统中。然而，MCP工具的使用也引入了新的安全风险，因为LLM代理可能被诱导执行恶意或未经授权的操作。尽管已有工作提出了保护LLM代理中工具使用的防御措施，但大多数方法依赖于静态分析，即检查提示和生成的输出，这限制了防御效果和鲁棒性。为解决这些局限性，我们提出了MTGuard，一种基于混合分析的防御框架，通过利用生命周期感知的静态-动态协同分析来保护LLM代理中MCP工具的安全使用。大量评估表明，MTGuard能够有效减轻不同LLM代理中多种类别的有害工具使用，同时保持良性用户任务的性能。

## Abstract
The rapid development of large language model (LLM) agents has enabled their broad adoption across diverse real-world tasks. To standardize interactions between LLM agents and external environments, Model Context Protocol (MCP) tools have emerged as a de facto standard and have been widely integrated into these systems. However, the use of MCP tools also introduces new safety risks, as LLM agents can be induced to perform malicious or unauthorized actions. Although prior work has proposed defenses for securing tool use in LLM agents, most methods rely on static analysis, i.e., inspecting prompts and generated outputs, which limits the defense effectiveness and robustness. To address these limitations, we propose MTGuard, a hybrid analysis-based defense framework designed to safeguard the use of MCP tools in LLM agents by leveraging lifecycle-aware static-dynamic co-analysis. Extensive evaluation demonstrates that MTGuard effectively mitigates multiple categories of harmful tool use across different LLM agents while maintaining performance on benign user tasks.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- 大语言模型（LLM）代理已广泛应用于真实世界的复杂任务中，其核心能力之一是通过调用外部工具与环境交互。Model Context Protocol（MCP）已成为连接 LLM 代理与外部工具/数据源的事实标准，但这一统一接口也引入了一条**关键安全边界**。
- 安全风险在于：一个不可信或被攻陷的 MCP 工具可能诱导代理执行恶意或未经授权的操作，例如工具投毒攻击、恶意参数注入、运行时执行敏感文件访问、拉起非预期子进程、与不可信端点通信等。
- 现有防御大多基于**静态分析**，仅检查用户提示、对话历史、工具元数据、参数和文本结果，而**无法观察工具执行期间产生的系统级副作用**。这构成一个根本性盲区：恶意工具在元数据和返回消息上可以表现正常，却在运行时执行危险行为。
- 传统沙箱/运行时监控虽能捕获低级系统调用，但存在“语义鸿沟”：同样的文件访问或网络请求在不同任务上下文中可能是良性或恶意的。因此需要把**协议级语义上下文**与**执行级动态证据**结合。
- 论文提出 **MTGuard**，一个基于生命周期感知的静态-动态协同分析框架，作为外部“守卫代理”保护 LLM 代理的 MCP 工具调用过程；它覆盖工具调用的整个生命周期（执行前、执行中、执行后），旨在同时检测静态分析方法看不见的运行时攻击。

## 2. 论文提出的方法论：核心思想、关键技术细节、公式或算法流程

### 2.1 核心思想

- **混合分析**：将“静态上下文”（用户任务、对话历史、工具名称/参数模式、声明调用参数）与“动态执行证据”（进程、文件、网络、DNS 行为）结合，根据“声明 vs 实际”的一致性判断工具调用是否安全。
- **生命周期感知**：按 MCP 工具调用划分为三个阶段——pre-execution、in-execution、post-execution，并在每个阶段设置对应组件。

### 2.2 形式化问题定义

- 状态转移：工具调用 \(T\) 导致状态从 \((c,e)\) 变为 \((\hat{c},\hat{e})\)，其中 \(c\) 为任务上下文，\(e\) 为环境状态。
- 若 \(\hat{c} \in C_{usf}\) 或 \(\hat{e} \in E_{usf}\)，则调用不安全。
- 安全调用集合：\(T_{safe}(c,e) = \{T \mid \hat{c} \notin C_{usf} \land \hat{e} \notin E_{usf}\}\)。
- MTGuard 的目标函数为：
  \[
  M(T;c,e)=
  \begin{cases}
  approve,& T\in T_{safe}(c,e)\\
  deny,& T\notin T_{safe}(c,e)
  \end{cases}
  \]

### 2.3 三大组件

1. **预执行参数审计器（Pre-execution Parameter Auditor）**
   - 在工具分发前分析声明的工具调用。
   - 收集对话历史、当前用户任务、工具名称、参数 schema 和参数；**故意剔除自由格式工具描述**，防止工具元数据投毒影响审计模型。
   - 先运行用户定义的**代码/程序化策略**（确定性函数），再运行**自然语言策略**（基于 LLM 的文本审计）。
   - 任一策略判定拒绝，则终止调用并返回拒绝响应。

2. **执行中行为监视器（In-execution Behavioral Monitor）**
   - 在 Docker 沙箱中执行 MCP 工具，通过宿主侧 **eBPF** 插桩捕获系统级事件。
   - 支持 cgroup v2 隔离，追踪容器内已有进程及其新派生子进程，记录进程创建/执行/终止、文件打开/删除/重命名、TCP 连接/监听、UDP DNS 响应等事件。
   - 引入新数据结构 —— **工具行为树（Tool Behavior Tree）**：
     - 以工具调用为根，包含进程分支和 DNS 分支；
     - 文件/网络事件关联到产生它们的进程节点；
     - 以进程亲缘关系和执行依赖组织异构运行时事件，将零散低层审计日志转化为可解释的工具行为描述。
   - 监视器本身不判决策略，只负责收集证据。

3. **后执行结果验证器（Post-execution Result Verifier）**
   - 在工具执行后，结合声明调用、执行结果、工具行为树和 DNS 事件，做“声明 vs 实际”的比对，检查实际行为是否与声明的功能一致。
   - 先将原始行为树简化（过滤 Python 字节码、共享库加载、回环流量等噪声）并截断过长记录，以控制 LLM 输入。
   - 同样先执行代码策略，再执行 LLM 文本策略；默认“允许”，仅在存在清晰不一致或显式策略违反时拒绝。
   - 若拒绝，则扣留工具结果并返回拒绝信息，但无法回滚已完成副作用。

### 2.4 威胁模型

- 覆盖三类攻击面：**MCP 服务端攻击**（控制工具元数据/实现/返回载荷）、**MCP 宿主端攻击**（篡改规划、消息路由、工具调用分发）、**用户端攻击**（恶意提示、恶意文件）。
- 假设每次攻击只攻陷一个攻击面，防御系统本身可信，排除训练时攻击、内核级攻陷、多攻击面合谋等。

## 3. 实验设计：数据集 / 场景、基准、对比方法

### 3.1 场景与数据

- 基于 **MCP-SafetyBench** 的两个代表性安全关键领域：
  - **浏览器自动化代理**（Playwright MCP 服务器为主，涉及航班预订、地图搜索、Hugging Face、学术论文检索、体育网站等）；
  - **金融分析代理**（Yahoo Finance MCP 服务器为主）。
- 额外引入 16 个新的 **MCP 宿主端 Tool Call Hook** 攻击用例（每域 8 个），模拟攻击者劫持代理生成的良性工具调用，替换为 `terminal::run_command` 并执行未授权 shell 命令（如 `cat /etc/passwd`）。
- 最终评估套件含 **99 个攻击用例**：
  - 62 server-side、26 host-side、11 user-side；
  - 覆盖 18 个细粒度攻击类别（工具投毒、函数重叠、偏好操纵、工具遮蔽、函数返回注入、rug-pull、意图注入、数据篡改、重放注入、恶意代码执行、凭据窃取、远程访问控制、Tool Call Hook 等）。

### 3.2 代理与后端 LLM

- 实现 ReAct 风格代理，每个代理实例化 3 种后端 LLM：
  - DeepSeek-V4-Flash
  - DeepSeek-V4-Pro
  - GPT-5.6 Luna
- MTGuard 的文本级策略审计统一使用 **DeepSeek-V4-Pro** 作为后端审计 LLM。

### 3.3 基线方法

- 对比 Agent-Aegis 的两个运行时防御组件：
  - **Tool Call Governance (TCG)**：执行前检查工具名和参数，基于高危及混淆 shell 命令规则；
  - **Tool Result Inspection (TRI)**：执行后扫描工具返回文本中的注入/泄露模式。
- 为公平比较，基线被重放到 MTGuard 采集的同一组工具调用轨迹上。

### 3.4 评估指标

- **DR（检测率）**：不安全调用中被查出的比例；
- **FPR（假阳性率）**：安全调用中被误判拒绝的比例；
- **审计延迟**：预执行和后执行 LLM 审计的平均耗时。

## 6. 论文的主要结论与发现

- MTGuard 在总体 DR 上显著优于基线：检测 116/240 个不安全调用，DR=48.3%；TCG 仅 8.3%，TRI 为 0%。
- 对 **host-side 攻击**效果突出（DR=75.0%），主要归功于行为监视和后执行验证能识别“声明调用与实际命令不一致”的工具调用劫持；TCG/TRI 完全无法检测这类攻击。
- 对 **user-side 攻击**达到 100% 检出，因为恶意命令/敏感路径通常直接出现在声明参数中。
- 对 **server-side 攻击**检出率较低（32.5%），因为此类攻击常用语法合法、语义看似正常的参数操纵合法工具，运行时轨迹接近正常。
- FPR 平均 3.7%，低于实用容忍度；延迟可接受（预执行约 5.7–5.9 秒，后执行约 6.4–6.7 秒，合计约 12.4 秒/调用）。
- 消融实验表明：PRA-only 和 PRV-only 分别为 25.0%、31.7%，均显著低于完整系统的 48.3%，且两阶段互补（PRA 擅长 user-side，PRV 擅长 host-side），证明静-动协同分析的必要性。

## 7. 优点

1. **思想创新**：明确指出现有静态防御的“运行时不可见”盲区，并首次将协议级上下文与沙箱执行证据系统性地结合。
2. **架构设计合理**：按 MCP 工具生命周期分三阶段防护，分工清晰，且前、后阶段都有代码级与文本级双层策略，兼顾效率与语义分析。
3. **工具行为树**：比普通进程树更具表达力，能将异构运行时事件按执行依赖组织成可解释的安全分析结构，具有推广价值。
4. **安全性设计细致**：审计时主动排除工具描述，防止元数据投毒污染守卫模型；威胁模型明确，攻击面划分清晰。
5. **实验规范**：消融、误报、延迟、攻击有效性验证均齐全；采用 counterfactual enforcement 保证公平对比；新增 Tool Call Hook 攻击丰富了 benchmark。
6. **实用性强**：在低误报和可接受延迟的前提下实现可观的安全提升，适合作为安全敏感 LLM 代理部署时的防护层。

## 8. 不足与局限

1. **运行时可见性有限**：eBPF 只捕获进程/文件/网络/DNS 元数据，不检查网络载荷或应用层数据流，对加密流量、内存内计算、外部服务侧恶意行为难以检测。
2. **无法回滚副作用**：后执行验证只能抑制结果返回，不能撤销已经发生的系统级改动（如文件写入、持久化安装）。
3. **泛化受限**：当前原型和评估仅针对本地部署的 MCP 工具；远程工具或无法提供沙箱/系统追踪的平台难以直接适配。
4. **检测率上限不高**：整体 DR 仅 48.3%，对 server-side 攻击的检测率尤其低（32.5%），说明语义操纵类攻击仍是难点。
5. **基准与对比范围有限**：仅对比两种规则型基线，未与其他状态无关但更强的防御方法（如 GuardAgent、ShieldAgent、包级静态扫描等）在同一框架下对比。
6. **计算开销粗粒度**：只报告单次 LLM 审计延迟，未分解 eBPF 监控、沙箱启动、行为树构建等成本，也未给出端到端总开销。
7. **威胁模型假设偏保守**：排除多攻击面合谋、训练时攻击、内核级攻陷等更复杂场景，实际部署时面临的安全威胁可能更严峻。

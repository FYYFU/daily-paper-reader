## 摘要
AI代理正从咨询界面转向执行关键操作的系统：发放退款、预订稀缺库存、配置云资源以及发起金融转账。这些工作流需要对效果进行治理，而不仅仅是对模型输出进行治理。现有的安全措施通常根据请求发起时可得的信息来决定是否允许某个操作。对于有状态策略，请求时的视图可能是不完整的：预算、库存、审批状态和风险信号可能在效果发生之前发生变化，从而使先前的授权或批准失效。本文研究了并发代理系统的有状态治理。我们将失效授权识别为核心故障模式，并定义了策略状态可串行性，这一正确性条件要求已提交的效果可以被解释为在效果发生之前立即针对策略状态进行的授权。我们提出了Provenact，一种运行时架构，将策略保持为可审查的程序，同时协调维护其决策所需的状态和效果。在使用PostgreSQL支持的Provenact原型进行的实验中，该系统阻止了将策略状态作为普通请求上下文传递的基线方法所遗漏的失效授权，在不相关工作进行时保留延迟批准，使策略演进主要发生在策略文本而非受信任的提供者代码中，并在一个脚本化的、无LLM的采购工作流中避免了策略违规，而代理治理基线在共享预算和库存上产生了失效授权。更广泛地说，Provenact为将有状态治理边界集成到代理框架和提供者支持的领域（代理作用于共享资源）提供了一条路径。

## Abstract
AI agents are moving from advisory interfaces into systems that execute consequential operations: issuing refunds, reserving scarce inventory, provisioning cloud resources, and initiating financial transfers. These workflows require governance over effects, not only over model outputs. Existing safeguards often decide whether an action is allowed from the information available when the action is requested. For stateful policies, that request-time view may be incomplete: budgets, inventory, approval status, and risk signals can change before the effect occurs, making an earlier authorization or approval stale.   This paper studies stateful governance for concurrent agentic systems. We identify stale authorization as the core failure mode and define policy-state serializability, a correctness condition requiring committed effects to be explainable as authorized against the policy state immediately before they occur. We present Provenact, a runtime architecture that keeps policies as reviewable programs while coordinating the state and effects needed to preserve their decisions. In experiments with a PostgreSQL-backed prototype of Provenact, the system prevents stale authorizations missed by baselines that pass policy state as ordinary request context, preserves delayed approvals while unrelated work proceeds, keeps policy evolution mostly in policy text rather than trusted provider code, and avoids policy violations in a scripted, LLM-free procurement workflow where agent-governance baselines produce stale authorizations over shared budgets and inventory. More broadly, Provenact suggests a path for integrating stateful governance boundaries into agent frameworks and provider-backed domains where agents act on shared resources.

## 1. 核心问题与研究动机

- **背景**：AI 代理正从"咨询式界面"演变为执行实际关键操作的系统——发放退款、预订稀缺库存、配置云资源、发起金融转账等。这些工作流需要对"效果"（effects）进行治理，而不仅仅是过滤模型输出。
- **核心问题**：现有安全机制通常在请求发起时根据当时可得的信息决定是否允许操作。但对于依赖**可变策略状态**（预算、库存、审批状态、风险信号等）的有状态策略，请求时的视图可能不完整——在策略决策与效果实际提交之间，其他并发操作可能改变这些状态，导致先前的授权或批准**过期失效**。
- **关键失败模式**：作者将其命名为 **stale authorization（陈旧授权）**——系统基于某个"允许"决策执行操作，但该决策所依赖的状态事后已经改变。其长期形态是 **stale approval（陈旧批准）**：人工审批在请求时正确，但到批准生效时，相关预算/库存已被其他操作消耗。
- **具体示例**：同一团队的两个代理从不同账户各转 1 个信用额；团队已花费 9/10 信用额。两个操作各自单独检查时都合法，但若都提交，团队总花费达 11，违反预算。
- **现有方案的不足**：
  - 请求本地策略引擎（Cedar、AGT、Omnigent 等）保持模块化，但将保护"允许决策背后状态"的责任留给了调用方；
  - 全局锁虽正确，但牺牲并发与延迟审查；
  - 手写事务只强制单一固定策略，且把策略逻辑埋入受信任的工具代码，破坏策略模块化。

## 2. 方法论

### 2.1 核心思想

Provenact 的核心是在"策略引擎决策"与"被治理效果"之间建立一个**有状态的治理边界**，使策略保持一致为一等公民的可审查程序，同时协调状态与效果的原子性。

### 2.2 关键概念与定义

- **策略状态（Policy State, S）**：决定所有已部署有状态策略所需的逻辑状态（可消耗容量、历史记录、审批等），是策略可能查询的全部治理事实，而非整个应用数据库。
- **治理操作（Governed Operation）**：请求表示为 `req = (principal, action, args)`；扩展为含策略评估、效果结果与审计结果的操作。
- **认证策略状态视图**：`Q(S, req) → v`，策略可调用的受信任只读投影函数。
- **有状态策略**：读取由被治理系统维护的可变策略状态的策略程序（如 `budget.spent(principal.team, 24h) + args.amount > budget.limit(...)`）。
- **策略状态可串行性（PSS）——本文核心正确性条件**：
  - 定义：并发历史 H 满足 PSS，当存在一个串行历史 serial(H)，满足：① 保持 H 的实时顺序；② 每个终态决策在其串行位置前立即依适用策略评估匹配；③ 每个允许操作在该位置应用其治理效果；④ 每个拒绝操作不产生效果；⑤ 串行历史与 H 产生相同的治理效果和最终策略状态。
  - 等价地，每个终态操作 `i` 的决策为 `d_i = P_i(req_i, Q_i(S_i, req_i))`，下一状态为 `S_{i+1} = E_i(S_i, req_i)`（若 allow）或保持 `S_i`（若 deny）。
- **策略诱导冲突**：当操作 `i` 的效果写集合 `W_i^E` 与操作 `j` 的策略读集合 `R_j^P` 重叠时构成策略级冲突——即使应用层写入完全不相关（如不同账户）。
- **定理 1**：若部署策略良类型且有界、提供者契约健全、所选强制机制在记录终态决策前和允许效果提交前对重叠逻辑作用域进行串行化/预留/校验，则运行时产生的每个终态历史都满足 PSS。

### 2.3 Provenact 运行时架构

运行路径：请求规范化 → 依赖与作用域解析 → 作用域强制 → 策略评估 → 策略状态效果提交 → 治理记录更新；支持升级（escalation）处理。

- **策略程序与提供者契约**：
  - 认证策略状态视图契约：声明类型化视图接口、受信任解析器、作用域解析器（将视图参数映射到有限逻辑作用域集合），并标识是否为可消耗容量/已消耗容量/需在提交时重查的状态。
  - 效果契约：声明动作模式、所需一致性保证、策略状态足迹解析器、受信任执行器。
  - 示例：预算视图 `budget.spent(team, window)` 映射到作用域 `team-budget:{team}`，转账效果声明读写同一作用域。
- **作用域强制（Scoped Enforcement）**：协调器先获取作用域上的本地键锁；对 PostgreSQL 后端，还在资源会话内获取事务级顾问锁。同一会话用于策略评估、效果执行、预留更新、幂等检查和治理记录写入。
- **两种强制模式**：
  - **事务模式（Provenact-Tx）**：在受保护作用域的事务内完成策略评估与效果提交；
  - **预留模式（Provenact-Res）**：为长期审批或高竞争资源创建/消耗持久容量记录（escrow 风格），使竞争操作可立即被拒绝。
- **协议语言与静态检查**：策略是有界、无副作用的一阶纯函数，仅可调用已注册的认证视图；编译器拒绝未注册视图、嵌套视图调用、缺少默认规则、类型错误、突变、循环和任意回调。
- **升级处理**：升级视为分阶段治理操作——初始策略评估记录待处理操作（非终态）；在预留模式下同时预留相关容量；解决时消耗预留或重新校验策略状态后才提交效果。

## 5. 主要结论与发现

1. **RQ1（正确性）**：Naive 和 Cedar 在最小冲突中两笔都提交（各产生 1 次陈旧授权）；全冲突中产生 30–31 次陈旧授权、提交约 80 笔（预算只允许 50 笔）。所有正确性保持模式（Global、Manual tx、Provenact-Tx、Provenact-Res）恰好提交 50 笔、拒绝其余、零陈旧授权、满足 PSS。
2. **RQ2（效率）**：0ms 服务时间时 Provenact-Tx 达 88.9 ops/s（约 Global 的 0.87 倍，与 Manual tx 持平）；10ms 时达 86.4 ops/s，为 Global 的 **1.64 倍**。全局串行化随服务时间增长显著退化，而作用域级强制可并行推进。
3. **RQ3（人工审查）**：纯重新校验（Global revalidation、Provenact-Tx）避免陈旧提交但 100% 使待审批失效（竞争操作先提交）；Provenact-Hold 和 Provenact-Res 均 100% 保留审批且允许全部无关工作完成。在 64 团队高竞争下，Provenact-Res 保留审批的同时实现 12.4% 固定窗口进度（优于 Hold 的 7.5%），因为它用预留立即拒绝竞争操作而非让竞争方等待。
4. **RQ4（模块性）**：5 种策略演进中 Provenact 仅修改 18 行策略代码和 4 行受信任提供者代码；手动基线需修改 22 行受信任代码。新增策略状态输入（每代理历史、审批计数、风险分数）只需注册小型契约，转账效果执行器不变。
5. **RQ5（代理工作流）**：AGT 平均提交 71.6 个（59.0 个有效），其原生 CostGuard 消除日成本违规但每轮都留下团队预算和库存违规；Omnigent 提交 107.6 个（66.2 个有效），三类状态均违规；Provenact-Tx 和 Provenact-Res 各提交 70.6 个且全部有效，零陈旧决策、零最终状态违规，通过预留保留了全部 13.8 个审批基础。

## 6. 方法亮点（优点）

1. **形式化正确性定义**：PSS 首次为有状态治理给出可验证的正确性条件，将授权决策与效果提交绑定在统一串行解释下，兼顾实时顺序与审计语义。
2. **清晰的抽象边界**：策略作者编写有界纯策略程序，提供者声明契约，运行时做作用域强制——三者职责分离，"信任边界"明确。
3. **作用域强制而非全局串行化**：只协调策略状态依赖冲突的操作，允许不相关操作并发推进，避免全局锁的性能代价。
4. **区分两类正确性**：将"终态历史满足 PSS"（重新校验即可）与"保留待审批的策略状态基础"（需预留/持有）明确区分，揭示人工审查场景下纯数据库正确性不足。
5. **完善的基线对照组**：覆盖从朴素 check-then-act、外部策略引擎（Cedar）、原生代理治理工具（AGT、Omnigent）到手写事务、全局串行化等完整谱系，对比公平且具有针对性。
6. **诚实披露**：对 p95 延迟的种子敏感性、性能指标的绝对开销、原型的未完善之处均明确说明，降低偏差风险。

---

## 7. 不足与局限

1. **实验覆盖有限**：全部为受控基准而非真实部署轨迹；RQ5 是脚本化、LLM-free 模拟，未验证真实 LLM 代理的开放行为与提示注入等场景。
2. **提供者信任边界较重**：Provenact 无法创造提供者本身无法保证的一致性——视图、效果、预留、幂等机制全部依赖受信任提供者实现；契约中若遗漏所需作用域，PSS 保证即失效。
3. **外部效果未覆盖**：无法参与数据库事务的外部 API（网络 I/O）不在当前设计范围内；论文承认需要一个持久的受保护执行协议（外部操作身份 + 幂等 + 对账）来处理，留作未来工作。
4. **策略语言受限**：有界纯函数限制排除了任意回调和不可界计算，这虽是必要的设计取舍，但限制了策略表达能力。
5. **原型范围窄**：无生产部署工具、策略包签名、具体代理框架 API 依赖；绝对吞吐包含 Python 编排和 PostgreSQL 会话开销，为原型级而非生产级表现。
6. **RQ3 性能权衡**：高度竞争下 Provenact-Hold/Res 的固定窗口进度显著低于纯重新校验模式（7.5%–12.4% vs 18%–100%），审批保留是有工程成本的。
7. **硬性要求**：所有治理效果和策略状态突变必须完全经过 Provenact 调解路径；直接数据库写入或绕过的管理脚本会使保证失效——这一"完全调解"要求在真实生产环境中较难严格满足。

## 8. 总体评价

本文将有状态治理问题明确定位为**并发控制问题**而非提示工程或评估问题，通过 PSS 形式化条件与 Provenact 运行时架构，在"可审查的策略程序"与"可靠的并发执行"之间架起了一座桥梁。其核心洞察——"allow 决策不是永恒的能力凭证，

其核心洞察——"allow 决策不是永恒的能力凭证，而是随策略状态瞬时变化的一次性判断"——准确揭示了现有 AI 治理栈中"策略判定即永久许可"这一隐含假设的缺陷。论文通过将治理问题重述为可串行化问题，使有状态策略的正确性不再依赖运行时偶然的时序，而是可被证明、可被审计的形式性质。这一工作对追求"可证明约束的代理执行"的研究方向（如 agentic access control、代理安全论证）具有直接的参考价值。

## 9. 适用读者与阅读建议

- **AI 安全与代理治理研究者**：重点关注 PSS 定义（§2.2）、定理 1 的适用条件（§2.3）以及 RQ1/RQ3 的结论——它们分别回答了"什么是正确"与"为什么纯数据库正确性对人工审批不够"这两个关键问题。

## 10. 结语

Provenact 的价值不在于提出新的策略语言或新的效果执行机制，而在于用 PSS 将"策略评估"与"效果提交"两个此前分离的阶段统一到同一串行解释下，明确指出二者之间存在一个必须被显式治理的时间窗口。这一窗口在单用户、请求-响应式交互中不可见，但在并发代理系统中成为安全性的决定性因素——这正是本文将"陈旧授权"确立为独立问题类别的意义所在。

论文的局限同样清晰：提供者契约的正确实现与"完全调解"假设在真实大规模部署中的履约成本尚未被充分检验；预留模式的容量管理（预留量额度、过期回收）也还需进一步工程化。但作为一篇问题定义精确、理论框架完整、实验对照严谨的系统论文，它为该领域后续研究提供了可复现的基准平台与可扩展的抽象语言。

**一句话总结**：当 AI 代理开始真正"做事"而非"说话"时，治理的关键不再是判断"这次请求该不该允许"，而是保证"允许时所依据的状态在效果落地那一刻仍然成立"——Provenact 为这一要求给出了形式化的语义、工程化的实现与系统的经验证据。
